1. บทนำ
1.1 ที่มาและความสำคัญ
บริษัทประกอบธุรกิจพัฒนาซอฟต์แวร์ ฮาร์ดแวร์ และ IoT ดำเนินกิจการมาประมาณ 3 ถึง 4 ปี มีลูกค้าและโครงการที่ปิดไปแล้วจำนวนมาก แต่ข้อมูลทั้งหมดถูกจัดเก็บในรูปแบบเอกสารกระดาษ และผูกติดกับความทรงจำของผู้บริหารเพียงคนเดียว
เมื่อจำเป็นต้องใช้ข้อมูล ต้องเสียเวลาค้นหาเอกสารย้อนหลัง ระยะเวลาการติดตามลูกค้าคลาดเคลื่อนไปเป็นเดือน และบางครั้งลืมไปว่ารายใดเคยเป็นลูกค้าของบริษัท ปัญหาเหล่านี้ส่งผลโดยตรงต่อความต่อเนื่องในการให้บริการและรายได้ที่ควรจะได้รับ
ระบบนี้จึงจัดทำขึ้นเพื่อเปลี่ยนข้อมูลที่กระจัดกระจายให้กลายเป็นฐานข้อมูลกลางแบบดิจิทัล ที่พนักงานใหม่สามารถเข้ามาทำงานต่อได้ทันที และมีระบบแจ้งเตือนเชิงรุกแทนการทำงานแบบตั้งรับ

2.3 รูปแบบการเชื่อมต่อ
ระบบใช้ RESTful API รับส่งข้อมูลในรูปแบบ JSON ยืนยันตัวตนด้วย JWT ที่ส่งมาใน HTTP Authorization Header และจัดทำเอกสาร API อัตโนมัติด้วย Swagger
เหตุผลเชิงเทคนิค  NestJS เป็นเฟรมเวิร์กสำหรับพัฒนาส่วนหลังบ้านโดยเฉพาะ มีโครงสร้างแบบ Module, Controller และ Service ซึ่งใช้แนวคิดเดียวกับ Angular ทำให้ทีมที่ถนัด Angular เข้าใจได้ทันที อีกทั้งมีกลไก Guard สำหรับตรวจสอบสิทธิ์ และ Interceptor สำหรับบันทึกการใช้งาน ซึ่งตรงกับข้อกำหนด SC-4 และ SC-5 ของระบบนี้

3. ผู้ใช้งานระบบและสิทธิ์การเข้าถึง
ระบบไม่กำหนดสิทธิ์แบบตายตัวไว้ล่วงหน้า แต่ออกแบบให้ผู้ดูแลระบบสร้างบทบาทและกำหนดสิทธิ์ได้เองทั้งหมด เพื่อรองรับกรณีที่พนักงานหนึ่งคนรับผิดชอบงานมากกว่าหนึ่งด้าน
3.1 ระดับบัญชีผู้ใช้
ระบบแบ่งบัญชีผู้ใช้เป็นสามระดับ แตกต่างกันที่ขอบเขตการจัดการ ไม่ใช่ขอบเขตการใช้งานโมดูล
ระดับ
สิทธิ์เฉพาะตัว
ที่มาของบัญชี
Super Admin
ทำได้ทุกอย่าง และเป็นระดับเดียวที่สร้างหรือแก้ไขบทบาทได้
กำหนดไว้ตั้งแต่ติดตั้งระบบ ไม่ต้องเลือกบทบาทให้
Admin
เข้าถึงได้ทุกเมนู เพิ่มผู้ใช้และเพิ่ม Admin ด้วยกันได้ แต่แก้ไขบทบาทไม่ได้
แต่งตั้งโดย Super Admin
User
เข้าถึงได้เฉพาะเมนูตามบทบาทที่ได้รับ
เพิ่มโดย Admin หรือ Super Admin
จุดสำคัญ  การสร้างและแก้ไขบทบาทถูกสงวนไว้ที่ Super Admin เท่านั้น ไม่ใช่สิทธิ์ที่ติ๊กเลือกได้ เพื่อป้องกันไม่ให้ผู้ใช้ทั่วไปยกระดับสิทธิ์ตนเอง
3.2 กลไกการกำหนดสิทธิ์
ภาพที่ 3.1  ความสัมพันธ์ระหว่างระดับบัญชี บทบาท และสิทธิ์

การดำเนินการ

1
สร้างบทบาท

2

เลือกว่าบทบาทนั้นเข้าถึงเมนูใดได้บ้าง และทำอะไรได้บ้างในเมนูนั้น
3
ผูกบทบาทให้ผู้ใช้
เมื่อมีพนักงานใหม่ เพียงเลือกบทบาทที่มีอยู่แล้วให้ ไม่ต้องสร้างใหม่
3.3 หลักการยืดหยุ่นของบทบาท
ผู้ใช้หนึ่งคนถือได้หลายบทบาทพร้อมกัน สิทธิ์ที่ได้รับคือผลรวมของทุกบทบาท

เห็นเมนูของทั้งสองบทบาทรวมกัน
เหตุผลของการออกแบบ  หากกำหนดสิทธิ์ตายตัวไว้ในโปรแกรม จะไม่รองรับกรณีที่พนักงานหนึ่งคนรับผิดชอบงานหลายด้าน และทุกครั้งที่โครงสร้างองค์กรเปลี่ยน จะต้องแก้ไขโปรแกรมใหม่ การให้ผู้ดูแลระบบกำหนดเองจึงยืดหยุ่นกว่าและไม่ต้องแก้โค้ด
3.4 สถานะของผู้ใช้งาน
เมื่อพนักงานลาออกหรือสิ้นสุดการฝึกงาน ระบบจะไม่ลบบัญชีทิ้ง แต่เปลี่ยนสถานะแทน เพื่อให้บันทึกการใช้งานย้อนหลังยังอ้างอิงได้ว่าใครเป็นผู้ดำเนินการ
