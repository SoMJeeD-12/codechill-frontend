# สิ่งที่ต้องขอจาก Backend

รวมรายการที่หน้าจอออกแบบไว้แล้วแต่ API ปัจจุบันยังทำให้ไม่ได้
ทุกข้อในนี้ **ห้ามทำเหมือนใช้ได้จริงบนหน้าจอ** — ให้ซ่อน หรือติดป้าย "ตัวอย่าง" ชัดเจน

อัปเดตล่าสุด: 12 ก.ย. 2569

---

## 1. สถานะ "ส่งงานให้ผู้รับผิดชอบแล้ว"

**ต้องการ:** สถานะใบแจ้งปัญหาที่บอกว่า *หัวหน้ามอบหมายแล้ว แต่ผู้รับผิดชอบยังไม่เริ่มทำ*

**ตอนนี้:** `TicketStatus` มีแค่ `RECEIVED` · `IN_PROGRESS` · `RESOLVED` · `REOPENED` · `CLOSED`
เมื่อกด `PATCH /api/tickets/:id/assign` สถานะยังเป็น `RECEIVED` เหมือนเดิม
ทำให้แยกไม่ออกระหว่าง "ยังไม่มีใครรับ" กับ "มอบหมายแล้วรอเริ่ม"

**ขอ:** เพิ่มสถานะ `ASSIGNED` (หรือ flag `isAssigned`) และให้ `/assign` เปลี่ยนสถานะให้อัตโนมัติ

**สถานะบนหน้าจอตอนนี้:** ซ่อน — หน้ารายการแสดงแค่สถานะจริงจาก API

---

## 2. หมวดหมู่ปัญหา (Ticket Category)

**ต้องการ:** จัดกลุ่มใบแจ้งปัญหาเพื่อดูว่าปัญหาประเภทไหนเกิดบ่อย

**ตอนนี้:** `POST /api/tickets` ไม่มีฟิลด์หมวดหมู่ และไม่มี endpoint จัดการรายการหมวดหมู่

**ขอ:**
- ตาราง/endpoint `GET /api/ticket-categories` (หรือ enum คงที่)
- ฟิลด์ `categoryId` ใน `POST /api/tickets` + `GET /api/tickets?categoryId=`

**สถานะบนหน้าจอตอนนี้:** ซ่อน — ไม่มีช่องหมวดหมู่ในฟอร์มเปิดใบ

---

## 3. เตือนโควตา MA ตอนเปิดใบแจ้งปัญหา

**ต้องการ:** ตอนพนักงานเปิดใบให้ลูกค้าที่มีสัญญา MA ระบบควรเตือนว่า "โควตาเหลือ 2 ครั้ง"

**ตอนนี้:** `GET /api/ma-contracts/:id/quota` ต้องรู้ `contractId` ก่อน
แต่ตอนเปิดใบเรารู้แค่ `customerId` / `projectId` — ต้องยิงหลายรอบ (list contracts → หา active → ดึง quota)
ซึ่งช้าและไม่การันตีว่าเจอสัญญาที่ถูกต้อง

**ขอ:** endpoint เดียวที่ตอบจาก customer/project เช่น
`GET /api/ma-contracts/quota-summary?customerId=&projectId=` → `{ contractId, used, total, remaining, isCurrentlyActive }`

**สถานะบนหน้าจอตอนนี้:** ซ่อน — ฟอร์มเปิดใบไม่มีแถบเตือนโควตา

---

## 4. ประกันผูกกับแผน MA

**ต้องการ:** ออกประกันแล้วให้ระบบรู้ว่าประกันนี้ต่อเนื่องเป็นสัญญา MA แผนไหน

**ตอนนี้:** `POST /api/deliveries/:id/warranties` ไม่รับ `maPlanId` / `maContractId`
และ `WarrantyResponseDto` ไม่มีฟิลด์อ้างอิงแผน MA

**ขอ:** ฟิลด์ `maPlanId` (optional) ตอนออกประกัน + คืนค่าใน response

**สถานะบนหน้าจอตอนนี้:** ซ่อน — ฟอร์มออกประกันกรอกแค่ระยะเวลา

---

## 5. รายงานรายโปรเจค

**ต้องการ:** หน้ารายงานที่สรุปตัวเลขของโปรเจคเดียว (งาน ส่งมอบ ปัญหา ชั่วโมงที่ใช้)

**ตอนนี้:** `/api/reports/*` ทั้งหมดสรุประดับบริษัท/ลูกค้า/ประเภท ไม่มีตัวกรอง `projectId`
- `GET /api/reports/contract-value/by-customer` · `/by-type` · `/upcoming`
- `GET /api/reports/service-cost`
- `GET /api/reports/ma-contract-overlaps`

**ขอ:** `GET /api/reports/project-summary?projectId=` หรือเพิ่มพารามิเตอร์ `projectId` ในรายงานที่มีอยู่

**สถานะบนหน้าจอตอนนี้:** ซ่อน — หน้ารายละเอียดโปรเจคไม่มีแท็บรายงาน

---

## 6. พิมพ์ใบยืนยันการแก้ไข

**ต้องการ:** ปุ่มพิมพ์ใบสรุปการแก้ไขปัญหาให้ลูกค้าเซ็นรับ

**ตอนนี้:** มีแต่ `GET /api/ma-contracts/:id/print` (สัญญา MA เท่านั้น)
ฝั่งใบแจ้งปัญหาไม่มี endpoint สร้างเอกสาร

**ขอ:** `GET /api/tickets/:id/print` คืน PDF (แนบ Authorization header · ดึงเป็น blob เหมือน `/documents/:id/download`)

**สถานะบนหน้าจอตอนนี้:** ซ่อน — หน้ารายละเอียดปัญหาไม่มีปุ่มพิมพ์

---

## 7. รหัสอัตโนมัติ (Auto-generate code)

**ต้องการ:** เปิดใบ/สร้างโปรเจค/สร้างลูกค้าแล้วได้รหัสอัตโนมัติ เช่น `TK-2569-0001` · `PJ-2569-0012`

**ตอนนี้:** `ticketNo` · `project.code` · `customer.code` เป็น `string | null`
ถ้าไม่กรอกจะได้ `null` และหน้าจอต้องแสดง "—"

**ขอ:** ให้ backend สร้างรหัสให้เองตอน POST เมื่อ client ไม่ส่งค่ามา (running number ต่อปี)

**สถานะบนหน้าจอตอนนี้:** คอลัมน์รหัสแสดงอยู่ แต่ค่าว่างแสดง "—" และยังไม่บังคับกรอก

---

## 8. Timeline วันที่รายรอบการแก้ไข

**ต้องการ:** ไทม์ไลน์ของใบแจ้งปัญหา — รับเรื่องเมื่อไหร่ มอบหมายเมื่อไหร่ เริ่มแก้เมื่อไหร่ แต่ละรอบใช้เวลาเท่าไร

**ตอนนี้:** `Ticket` มี `reportedAt` · `firstResponseAt` · `resolvedAt` · `closedAt` (ระดับใบ)
`TicketResolution` มี `startedAt` · `resolvedAt` · `hoursSpent` (ระดับรอบ) — แต่ไม่มีเวลา "มอบหมาย"
และไม่มี endpoint รวมเหตุการณ์ทั้งหมดเรียงตามเวลา

**ขอ:** `GET /api/tickets/:id/timeline` → รายการ `{ type, occurredAt, actorUserId, detail }`
(หรืออย่างน้อยเพิ่ม `assignedAt` ใน `TicketResponseDto`)

**สถานะบนหน้าจอตอนนี้:** ทำได้บางส่วน — แสดง "รายการรอบการแก้ไข" จาก `resolutions` ที่มีจริง
ไม่มีไทม์ไลน์เหตุการณ์เต็มรูปแบบ

---

## 9. ระบบแจ้งเตือน (กระดิ่ง)

**ต้องการ:** กระดิ่งแจ้งเตือนบนแถบบน — งานที่ถูกมอบหมาย ใบที่เลยกำหนด ประกันใกล้หมด

**ตอนนี้:** **ไม่มี endpoint ใด ๆ** สำหรับ notification
ของเดิมในโค้ดเป็น mock ล้วน (`core/mock/notification.mock.ts`) เก็บใน localStorage

**ขอ:**
- `GET /api/notifications?unreadOnly=` → `{ items, total, page, limit }`
- `PATCH /api/notifications/:id/read`
- `PATCH /api/notifications/read-all`

**สถานะบนหน้าจอตอนนี้:** **ถอดออกแล้ว** — ไม่มีกระดิ่งบนแถบบน และไม่มีเมนู "การแจ้งเตือน"
เพราะข้อมูล mock ทำให้ผู้ใช้เข้าใจผิดว่าระบบเตือนจริง
งานที่ต้องทำวันนี้ย้ายไปแสดงบน **หน้าแรก** แทน (ใช้ข้อมูลจริงจาก API)

## 10. ⚠️ `search` ค้นภาษาไทยไม่เจอ — เร่งด่วนที่สุด

**อาการ:** พารามิเตอร์ `search` ใช้ได้เฉพาะตัวอักษรภาษาอังกฤษ
ถ้าส่งคำภาษาไทยเข้าไปจะคืน `total: 0` เสมอ ทั้งที่มีข้อมูลตรงอยู่จริง

**ทดสอบเมื่อ 12 ก.ย. 2569 (บัญชี somchai):**

| คำค้น | endpoint | ผลที่ได้ | ผลที่ควรได้ |
|---|---|---|---|
| `iot` | `/api/projects?search=iot` | 2 ✅ | 2 |
| `PRJ` | `/api/projects?search=PRJ` | 4 ✅ | 4 |
| `ระบบ` | `/api/projects?search=ระบบ` | **0 ❌** | 3 (ระบบรับปริญญา, ระบบจัดการคลังสินค้า, ระบบติดตามอุณหภูมิ…) |
| `เมิร์ฟ` | `/api/projects?search=เมิร์ฟ` | **0 ❌** | 1 |
| `บริษัท` | `/api/customers?search=บริษัท` | **0 ❌** | 3 |
| `โค้ดชิลล์` | `/api/customers?search=โค้ดชิลล์` | **0 ❌** | 1 |

**น่าจะเป็นเพราะ:** collation ของคอลัมน์ หรือการใช้ `LIKE`/`ILIKE` ที่ไม่รองรับ UTF-8
(ถ้าเป็น MySQL ลองเปลี่ยนเป็น `utf8mb4_unicode_ci` · ถ้าเป็น Postgres ตรวจ `ILIKE` + index)

**กระทบอะไร:** ทุกช่องค้นหาแบบเลือกข้อมูล (ลูกค้า / โปรเจค) ซึ่งชื่อเป็นภาษาไทยแทบทั้งหมด
— ถือว่าใช้งานจริงไม่ได้เลยถ้าไม่แก้

**ทำอะไรไปก่อนแล้ว:** ใส่ fallback ฝั่ง frontend
(`searchWithClientFallback` ใน `shared/components/entity-picker.component.ts`)
ยิง `?search=` ก่อน ถ้าได้ 0 รายการค่อยดึง `?limit=100` มากรองเองในเบราว์เซอร์

**ข้อจำกัดของ fallback:** กรองได้แค่ 100 รายการแรกเท่านั้น
พอข้อมูลเกิน 100 ราย จะเริ่มหาไม่เจอ — **ต้องให้ backend แก้จริง**
เมื่อแก้แล้ว fallback จะไม่ถูกเรียกเองโดยอัตโนมัติ (เพราะรอบแรกเจอผลลัพธ์) ไม่ต้องแก้ frontend ซ้ำ

## หมายเหตุเพิ่มเติม — ไม่ถึงขั้นบล็อกงาน แต่ทำให้หน้าจอดีขึ้นมาก

### ก. `GET /api/tasks` ไม่มีตัวกรอง `overdue`
มี `/api/tasks/overdue` แยกต่างหาก ซึ่งใช้ได้ แต่ถ้าเพิ่ม `?overdue=true` ใน `/api/tasks`
จะรวมกับตัวกรองอื่น (`assignedUserId` + `overdue`) ได้ในครั้งเดียว
ตอนนี้หน้าแรกต้องยิง 2 ครั้งแล้วมา intersect ฝั่ง client

### ข. `GET /api/customers` ไม่มี `projectCount`
หน้ารายการลูกค้าอยากโชว์ว่าลูกค้ารายนี้มีกี่โปรเจค (เพราะโปรเจคคือพระเอก)
ตอนนี้ต้องยิง `/api/projects?customerId=` ทีละราย — ทำไม่ไหวในหน้ารายการ

### ค. `POST /api/communication-logs` ไม่มีตัวเลือกสร้างงานติดตามต่อ
ปิดงานติดตามแล้วเราถามผู้ใช้ว่า "บันทึกการติดต่อเลยไหม" ซึ่งทำได้ด้วย 2 คำสั่ง
(`PATCH /follow-ups/:id/complete` แล้ว `POST /communication-logs`)
ถ้ามี atomic endpoint เดียวจะกันกรณีคำสั่งที่สองพัง
